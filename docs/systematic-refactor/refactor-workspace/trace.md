## Flow 1 — Cold page load

**Path:** index.html -> /loading.js + /src/index.jsx -> i18next locale fetch -> React mounts -> GET /api/settings (Config.jsx) -> Zustand fan-out -> map shell paints -> GET_MAP_DATA (GraphQL) -> icons/filters processed -> per-category polling queries start

### Narrative

Cold page load: browser requests index.html, which paints a static loading spinner immediately (no JS needed), then two deferred `type=module` scripts run in document order — /loading.js (pure localStorage read, sets dark-mode class and translated loading text, zero network) then /src/index.jsx. index.jsx's imports trigger Sentry init and i18next init synchronously at module scope; i18next-http-backend immediately fires a GET for locale JSON, this is the first real network request the app makes. React then mounts App, which wraps everything in a Suspense boundary keyed to i18n readiness — until locales load, only a text-swap component renders (the static #loader div is still what the user sees). Once translations resolve, ApolloProvider + BrowserRouter + Pages mount and match route "/" to `<Config><MapPage/></Config>`. Config.jsx renders null and fires GET /api/settings in a useEffect — this is the second network request, and it fully gates the map: nothing under Config renders until it resolves. Server-side, /api/settings does real work before responding: session read/write, an optional DB lookup for the user row when logged in, and a set of `Promise.allSettled` cache-refresh calls to the scanner backend gated by config flags (`api.queryOnSessionInit.*`) and the caller's permissions, then assembles the payload from three server-only UI-description generators (drawer, clientOptions, advMenus) plus mapConfig. The response fans out client-side inside Config.jsx into three separate Zustand stores via direct, unchecked property access (`data.map.general`, `data.clientMenus.pokemon.glow.sub`, `data.database.settings.userBackupLimits`, etc.) — there is no runtime schema or type guard, so a server response shape drift becomes a silent `undefined` or a thrown TypeError at read time, not a validation error at the boundary. Only after this setState call does Config render its children, and MapPage checks `auth.perms.map` (just populated) to decide whether to redirect anonymous users to /login or render the actual map shell (`<Container/>`), which mounts the real Leaflet `MapContainer` synchronously using whatever location/zoom is already in the (persisted) useStorage state. Inside the map, `<Effects/>` immediately calls `useMapData()`, firing the third and heaviest network request: `GET_MAP_DATA` over GraphQL, no variables, network-only. Its response (masterfile + filters + icons + audio + questConditions + supportsShinyStats) drives two more synchronous main-thread passes in a `useEffect`: building `UAssets` icon/audio URL-resolvers (no extra network calls — icon URLs are just composed strings, actual images load lazily per-marker later) and, separately, a `useStorage.setState` updater that runs `deepMerge({}, filters, prev.filters)` over the ~777KB filter tree plus several linear scans (Team Rocket key-migration logic, quest-condition-key migration, global-enabled propagation) — all synchronous JS on the same call stack, so it blocks input/rendering for its duration every time it runs (first load, hourly poll, and the icons-missing refetch). Only once `Icons` exists in useMemory AND the Leaflet map ref exists does `DataView` start rendering `FilterPermCheck` per drawer-provided category, each of which opens its own no-cache polled GraphQL query (pokemon 20s / gyms 10s / stations 15s / etc.) carrying a client-computed `filters: JSON` blob built by `trimFilters()`. So the real request order is: index.html → (parallel) locale JSON + main JS bundle → /api/settings → GET_MAP_DATA → N parallel per-category polling queries, with /api/settings and GET_MAP_DATA each individually blocking everything downstream of them, and only the first two blocking anything the user perceives as "loading" (the map shell itself paints before per-category data arrives). On the "arrives by three routes" question: build-time CONFIG (map.general.start{Lat,Lon,Zoom}, map.theme, api.polling, client.title) seeds Zustand's initial state and document.title at module-eval time; the SAME facts then arrive again in the /api/settings response (data.map.general.start\*, data.map.theme, data.api.polling, data.map.general.headerTitle) and Config.jsx's setState calls silently overwrite the build-time seed with the runtime value — a third source, persisted localStorage (already rehydrated into useStorage synchronously before either network call lands), wins over both for location/zoom if a prior session exists. Config.jsx itself is not a typed mapping: it is an untyped fan-out of raw chained property reads across three Zustand stores, trusting the server's JSON shape completely. Logged-out vs logged-in diverges at exactly two points: server-side, /api/settings skips the DB user lookup and derives session.perms from `authentication.alwaysEnabledPerms`/config defaults instead of `req.user.perms`; client-side, MapPage's `auth.perms.map` check (populated from whichever perms object the server returned) decides between rendering the map and redirecting to /login — an anonymous instance with no auth methods configured, or with map in alwaysEnabledPerms, renders the map identically to a logged-in one from this code path's perspective.

### Refactor notes

- **Three separate transport routes carry overlapping facts and the client has to know which one wins: build-time CONFIG (map.general.start{Lat,Lon,Zoom}, map.theme, api.polling, client.title) seeds Zustand's initial state and document.title, then /api/settings ships the SAME facts (data.map.general.start\*, data.map.theme, data.api.polling, data.map.general.headerTitle) as the authoritative runtime values that overwrite the build-time seed in Config.jsx. A third source, persisted localStorage, wins over both for location/zoom if present.**  
  _Evidence:_ vite.config.js:135-147; src/store/useMemory.js:84-85; src/store/useStorage.js:64-70; src/components/Config.jsx:66-82,123,135  
  _Bears on:_ 2.0 target replaces build-time bundled config with a schema+defaults model — this triple-source-of-truth pattern for the same facts (with silent last-write-wins semantics, no single source annotated as authoritative) is exactly the kind of implicit precedence rule a schema-first config should make explicit and enforced, not something to reproduce.
- **Config.jsx's entire fan-out of the /api/settings payload into Zustand is untyped property-chain access with zero runtime validation — every one of ~20 destructured paths (data.map.general, data.clientMenus.pokemon.glow.sub, data.database.settings.userBackupLimits, data.authentication.excludeList, etc.) will throw or silently produce undefined if the server's shape changes without the client changing in lockstep.**  
  _Evidence:_ src/components/Config.jsx:66-160  
  _Bears on:_ a TypeScript client (2.0 target) only helps here if the server also emits a schema the client validates against at the boundary — plain interface typing on the client alone doesn't stop a runtime shape drift from a server the type system never sees, since GraphQL/REST here carries no runtime enforcement at the wire.
- **GET_MAP_DATA's masterfile/filters/icons/audio round trip and its ~777KB deepMerge + regex-based Rocket-key + quest-condition migration logic run in full on every hourly poll and every icons-missing refetch, not just cold load — it's not a one-time bootstrap cost, it's a recurring main-thread stall.**  
  _Evidence:_ src/hooks/useMapData.js:12-30 (startPolling 1hr), 111-224 (deepMerge + migrations inside every data effect run)  
  _Bears on:_ 2.0's native-WebSocket-with-per-entity-deltas target directly attacks this: if masterfile/filters only change on actual server-side config edits (rare) rather than being re-fetched wholesale hourly, this entire migration/deepMerge pass collapses to 'run once, then apply small deltas' — worth designing the WS delta protocol to distinguish 'filter definitions changed' from 'entity data changed' so this doesn't get re-implemented as a bigger recurring cost.
- **/api/settings is not a pure config read — it performs a DB user lookup (when logged in) and Promise.allSettled scanner-backend cache refreshes gated by config flags, meaning the single request that blocks the entire client bootstrap (Config renders nothing until it resolves) has variable, backend-dependent latency baked in, on top of the JSON-assembly cost of three UI-generator modules.**  
  _Evidence:_ server/src/routes/rootRouter.js:173-194 (DB lookup), 196-249 (Promise.allSettled refreshes), server/src/utils/getServerSettings.js:12-71 (drawer/clientOptions/advMenus generation)  
  _Bears on:_ 2.0's Golbat-HTTP/gRPC-only + normalized rules-table target should separate 'what UI can this user see' (cheap, cacheable per-permission-set) from 'refresh backend availability caches' (I/O-bound, currently synchronous-blocking on first paint) — collapsing server-generated UI description generation into a static schema-driven client would remove the need for drawer/clientOptions/advMenus to run per-request at all.

## Flow 2 — Filter drawer to map update

**Path:** Drawer opens -> user expands Pokemon section -> clicks one Pokemon tile -> SelectorItem cycles its tri-state color and calls a useDeepStore setter -> one useStorage.setState call rewrites the filters.pokemon branch via setDeep -> zustand's persist wrapper synchronously JSON.stringifies the WHOLE store and writes it to localStorage before the click handler returns -> the store notification also re-renders QueryData(category="pokemon") because its `s.filters.pokemon` selector got a new object reference -> that re-render recreates buildVariables, which re-runs a `useEffect` whose body unconditionally calls refetchData() on every dependency change -> RobustTimeout.doRefetch either fires an Apollo refetch immediately (throttled to 500ms/5000ms) or defers to the next scheduled poll -> Apollo sends `filters: JSON!` (built by trimFilters) to POST /api/graphql -> Express/Apollo Server resolves `pokemon` -> server/src/models/Pokemon.js -> SQL against the scanner DB -> JSON array back -> QueryData filters out hideList ids -> Clustering.jsx buckets through Supercluster if over the per-category limit -> surviving children render as <PokemonTile> markers via react-leaflet.

### Narrative

The drawer itself is dumb: `src/features/drawer/index.jsx:49-93` just maps `useMemory(s => s.ui)` categories into `DrawerSectionMemo` accordions inside a MUI `Drawer`. Expanding the "pokemon" accordion (`components/Section.jsx:35-120`) flips `useStorage.setState({ sidebar: 'pokemon' })` (one more independent store write, unrelated to filters) and mounts `PokemonDrawerMemo` (`pokemon/index.jsx:22-75`), which reads the current tier via `s.getPokemonFilterMode()` (`store/useStorage.js:101-109`, derived from `filters.pokemon.easyMode` and `userSettings.pokemon.legacyFilter`) and renders `PokemonModeSelector`, the main/extra sliders tabs, and finally `SelectorListMemo category="pokemon"` for the "select" tab.

`SelectorList` (`components/SelectorList.jsx:52-277`) builds the grid's id list from `useMemory` (the server-shipped master filter set, part of the ~830KB masterfile), filters it by `onlyShowAvailable`/search from `useStorage`, and memoizes `items` (line 146). None of these dependencies change when a single Pokemon is toggled, so the list and its `VirtualGrid` (`components/virtual/VirtualGrid.jsx:49-88`, wraps `react-virtuoso`'s `VirtuosoGrid`) never re-render from a toggle — only the one virtualized cell does.

Each cell is `StandardItem` (`components/virtual/StandardItem.jsx:12-43`), which calls `useDeepStore(\`filters.pokemon.filter.${id}\`)` (`store/useStorage.js:193-241`) and hands `filter`/`setFilter`to`SelectorItem` (`components/virtual/SelectorItem.jsx`). Clicking the tile runs `handleClick` (lines 68-81): a tiny state machine that cycles red (disabled) -> green (`enabled:true, all:true`, uses global sliders) -> blue (`enabled:true, all:false`, per-form Advanced settings apply) -> red again, calling `setFilter(newFilter)`exactly once per click. In`easyMode` (basic tier) the green->blue step is skipped (`newFilter.enabled = !easyMode`), collapsing the tri-state to a simple on/off.

`setFilter` is the callback `useDeepStore` builds (`store/useStorage.js:193-234`): it calls `useStorage.setState(prev => ({ filters: setDeep(prev.filters, 'pokemon.filter.<id>', newFilter) }))` — a single store write per click. `setDeep` (`utils/setDeep.js:8-32`) walks the path and at each level does `obj[next] = {...obj[next]}` — it mutates the object it was handed (which is `prev.filters`, live store state) in place, then returns `{...obj}` up the chain. The net effect is a normal immutable-update-at-a-path: `filters.pokemon` and `filters.pokemon.filter` get fresh object references, `filters.pokemon.filter.<other-id>` and `filters.gyms`/`filters.pokestops`/etc. keep their old references untouched. That reference discipline is exactly what keeps the rest of the drawer and the other categories' `QueryData` instances from re-rendering.

Because `useStorage` is wrapped in zustand's `persist` middleware with no `partialize`, the wrapped `set` (`node_modules/zustand/esm/middleware.mjs:355-360`) calls the real `set(...)` first (notifying subscribers synchronously) and then, still inside the same call, `setItem()` (lines 337-349): `options.partialize({...get()})` — the identity function, so the ENTIRE store — is JSON.stringified and handed to `localStorage.setItem('local-state', ...)`. `toThenable` (lines 278-292) proves this chain is fully synchronous when serialize/storage are synchronous (they are: default `JSON.stringify` + real `localStorage`), so the write happens on the main thread, in the same tick as the click, before the event handler returns and before React has painted the new DOM.

The store notification also reaches `QueryData` (`pages/map/components/QueryData.jsx:114-181`), one instance per active category, mounted under `<DataView>`/`FilterPermCheck`. Its `filters = useStorage(s => s.filters?.pokemon)` selector now returns the new object, so the pokemon-category `QueryData` re-renders. That recomputes `buildVariables` (lines 149-164, a `useCallback` keyed on `filters`), which changes identity, which is a dependency of the `useEffect` at lines 192-203. React tears down and reruns that effect: it re-subscribes `map.on('fetchdata', refetchData)` and then unconditionally calls `refetchData()` immediately — this is the actual trigger for a filter-driven refetch; the `map.fire('fetchdata')` in `Container.jsx:29` only fires on pan/zoom (`moveend`/`zoomend`), not on a filter toggle.

`refetchData()` calls `timeout.current.doRefetch(buildVariables())` (`services/apollo/RobustTimeout.js:24-39`). If less than 500ms passed since the last update (or 5000ms if a fetch is already in flight, tracked by `AbortableContext._pendingOp`), the new variables are just stashed in `_pendingVariables` and dropped until the next scheduled `setLongTimeout` tick (up to the category's poll interval — 20s for pokemon). Otherwise it calls Apollo's `refetch(variables)` right away, which (via the `abortableContext` passed at `QueryData.jsx:171`) aborts any in-flight pokemon request through `AbortableContext.handle`/`_abort` (`services/apollo/AbortableContext.js:46-104`) before issuing the new one.

`buildVariables` builds `filters` via `trimFilters` (`QueryData.jsx:58-91`). It flattens the user's whole `filters.pokemon` object into a GraphQL `JSON!` scalar (`services/queries/pokemon.js:48-67`, `$filters: JSON!`): one `only<Key>` per top-level pokemon setting, `onlyLegacy`/`onlyLinkGlobal`/`onlyAllPvp`/`onlyAreas`, any `pvp*` userSetting, and then — critically — one entry per _enabled_ form, keyed by its raw id, holding its `PokemonFilter` fields minus `enabled`/`size` (`server/src/filters/pokemon/Frontend.js:5-54`: `iv`, `atk_iv`, `def_iv`, `sta_iv`, `level`, `cp`, `gender`, `xxs`, `xxl`, plus one array per configured PvP league, plus `all`/`adv` from `BaseFilter`). In `easyMode` this per-form value is swapped wholesale for the global `ivOr` slider settings (line 82-83), ignoring any individual customization. Each such entry serializes to roughly 200-350 bytes of JSON; a user with hundreds of forms enabled (a very common state, since "enable all then customize a few" is the normal flow) can push the `filters` variable into the tens-to-low-hundreds of KB, resent in full on every single toggle and on every 20s poll — much smaller than the ~777KB default-filters download, but non-trivial and fully re-sent even when only one bit changed.

### Refactor notes

- **The client/server filter contract is an untyped GraphQL JSON scalar built by hand-flattening a nested object (trimFilters, QueryData.jsx:58-91) into only<Key> keys, then re-parsed server-side into typed Filter classes (server/src/filters/pokemon/Frontend.js).**  
  _Evidence:_ src/services/queries/pokemon.js:55 `$filters: JSON!`; QueryData.jsx:70-71 dynamically builds keys via string concatenation from whatever properties exist on filters.pokemon.  
  _Bears on:_ 2.0 deletes GraphQL and replaces per-form filter maps with normalized user-authored rule tables — trimFilters and its only<Key> convention becomes entirely dead code, and the type-safety gap it papers over disappears by construction once filters are typed DB rows instead of a JSON blob.
- **A filter toggle triggers its refetch as a side effect of a useEffect dependency-array change (buildVariables identity), not as an explicit 'user changed a filter, send an update' action.**  
  _Evidence:_ QueryData.jsx:192-203 — the effect unconditionally calls refetchData() every time it reruns, and it reruns because buildVariables (a useCallback keyed on the filters selector) changed identity; RobustTimeout.js:24-39 exists specifically to throttle/dedup the resulting refetch storm.  
  _Bears on:_ The native WebSocket + per-entity-delta design in 2.0 should send an explicit 'filters changed' message rather than reconstructing this implicit-effect-plus-throttle pattern; the throttle/abort machinery (RobustTimeout + AbortableContext) is a workaround for the HTTP-poll model that a persistent socket connection wouldn't need.
- **zustand persist has no partialize, so every single checkbox click JSON.stringifies and localStorage-writes the ENTIRE store (all categories' filters, searches, tabs, menus, userSettings, icons, audio, webhookAdv...), synchronously on the main thread, confirmed at the zustand source level.**  
  _Evidence:_ node*modules/zustand/esm/middleware.mjs:337-360 (setItem wraps set, both run before the click handler returns) and 278-292 (toThenable proves it's synchronous for sync serialize+storage); useStorage.js:176-179 configures persist with only {name, storage}.  
  \_Bears on:* Directly actionable for the greenfield TS client: adding partialize (drop derived/ephemeral keys like searches/tabs/expanded from persistence) and/or throttling the write would remove a real per-click main-thread cost that scales with total store size, not just with what changed.
- **setDeep achieves its immutable-update-at-a-path behavior by mutating the object it's handed at each recursion level, relying on the fact that object already being a fresh shallow copy from the level above.**  
  _Evidence:_ src/utils/setDeep.js:14-16 `(obj[next] = Object.prototype.toString.call(obj[next]) === '[object Object]' ? {...obj[next]} : {})` — assigns into obj (its own parameter) rather than building a new object and returning it.  
  _Bears on:_ A naive TS port ('this just looks like it copies and returns, let me clean it up') could easily turn this into a real shared-reference mutation bug since the correctness depends on an easy-to-miss aliasing detail; needs an explicit reference-identity test (sibling keys unchanged, path keys new) before any rewrite, especially since there are zero frontend tests today.
- **The three filter tiers are not just a UI simplification layer — they change what data reaches the server. Basic mode discards all per-form Advanced customization and substitutes the global slider values for every enabled form; expert mode routes through an entirely separate 'legacy' string-filter model path server-side.**  
  _Evidence:_ QueryData.jsx:80-83 `easyMode ? requestedFilters.ivOr : specifics`; resolvers.js:271-278 branches Db.query(...,'getLegacy',...) vs 'getAll' on args.filters.onlyLegacy; git log shows a recent 'fix: disable legacy pvp calc' commit touching this same legacy path.  
  _Bears on:_ The 2.0 'ordered user-authored rules in normalized DB tables' design needs an explicit decision on whether basic-mode's behavior (ignore per-form state, apply one global rule to everything enabled) and expert-mode's separate legacy engine both need first-class representations in the new rule model, or whether one or both tiers are being deliberately dropped.

## Flow 3 — Poracle webhook manager

**Path:** Poracle webhook rule editor: client Zustand store -> Apollo mutation over a single untyped GraphQL field -> server resolver -> PoracleAPI REST client -> Poracle bot HTTP API -> response reconciled back via Apollo's uid-keyed normalized cache

### Narrative

ReactMap is not a thin proxy in front of Poracle — it is a caching, identity-translation, and UI-schema layer that owns real business logic Poracle itself does not have. At boot, EventManager (server/src/services/EventManager.js:54-64) constructs one PoracleAPI instance per configured, enabled webhook and seeds it from an on-disk cache for fast startup; a periodic getWebhooks() (EventManager.js:544-559) later re-fetches each Poracle's live config, geofences, and message templates over HTTP, version-gates it (must be >=4.8.4, server/src/services/Poracle.js:225-233), and republishes the merged object. So the server holds a standing local mirror of each Poracle instance's state, refreshed on an interval — the same "poll and cache" shape the audit already found for GET_MAP_DATA, just for webhook config instead of map data. On the wire, the entire feature funnels through one overloaded GraphQL field, `webhook(category: String, data: JSON, status: String): Poracle`, present nearly identically as both Query and Mutation (server/src/graphql/typeDefs/index.graphql:161,175) and resolved almost identically in both places (server/src/graphql/resolvers.js:577-605 and :737-770). The resolver's only real job is an auth check (perms.webhooks must include the user's selectedWebhook) and a dispatch to `Event.webhookObj[hook].api(userId, category, status, data)` — everything else is untyped JSON in, untyped JSON out. A concrete edit: on the "already tracked" list (TrackedTile.jsx), clicking Edit stores `{open:true, id, uid, category, onClose}` into the advanced slice of useWebhookStore (TrackedTile.jsx:84-95); the same effect also seeds `tempFilters[id]` from the live tracked row (TrackedTile.jsx:30-39). The WebhookAdvanced dialog, which is mounted unconditionally for every user via Nav.jsx, reads that slice and initializes two parallel pieces of local component state — `filterValues` (UI-friendly, e.g. min/max collapsed into slider ranges) and `poracleValues` (Poracle wire format) — via `Poracle.reactMapFriendly()` (client services/Poracle.js:151-178). Every slider/switch/select updates both in lockstep. Saving calls `handleClose(true, id, poracleValues)` (WebhookAdv.jsx:843), which merges the edited values into the store's tempFilters and then invokes the onClose callback captured in step one (WebhookAdv.jsx:827). That callback (TrackedTile.jsx:41-55) fires a bare `apolloClient.mutate` with `data: Poracle.processor(category, [newFilter], defaults)` — processor (client Poracle.js:180-301) is a hand-written per-category field allow-list/default-fill/dedup pass with no GraphQL or Poracle involvement at all, purely ReactMap's own domain logic. Apollo POSTs this to /graphql; the mutation resolver resolves the caller's Poracle user id via `PoracleAPI.getWebhookId` (server Poracle.js:126-139, picks discordId or telegramId depending on login strategy — an identity Poracle's REST API has no concept of on its own) and calls `.api()` (server Poracle.js:470-515), which for a tracking category (pokemon/raid/egg/etc.) dispatches to `#tracking()` (server Poracle.js:435-459). That method makes the actual outbound HTTP call — `POST /api/tracking/{category}/{userId}` with the row as body, secured by an `X-Poracle-Secret` header (server Poracle.js:289-300) — then immediately issues a second GET to the same collection endpoint to refetch the authoritative full list, sorts it by the UI's configured sortProp, and merges `{...first, ...second}`. Back in the resolver, the raw Poracle response is enriched with UI-only derived booleans Poracle's API never returns — `allForms`, `pvpEntry`, `xs`, `xl` for pokemon, `allMoves` for raid, `real_grunt_id` for invasion (resolvers.js:748-761) — before going back over the wire. On the client, no explicit refetch or state update follows the mutate call; this works because every Poracle GraphQL type is explicitly keyed by `uid` in Apollo's InMemoryCache typePolicies (src/services/apollo/index.js:15-44), so the mutation's response — which carries the same `uid` — is automatically normalized into any other active query (e.g. the Tracked list's `ALL_PROFILES` query in useGetWebhookData.js) without manual cache surgery. On the GraphQL-dependency question: essentially nothing here needs GraphQL specifically. The single `data: JSON` field carries no schema information the client and server don't already agree on by convention, the "fragments" only exist to describe response shape for Apollo's cache, and the one genuinely useful piece of Apollo machinery in play — automatic uid-based cache reconciliation after a mutation — is a client-cache feature, not a transport feature; a REST or WebSocket call returning the same JSON would need an equivalent explicit reconciliation step but nothing more. On bundle/permission gating: this is not lazy-loaded at all. Webhook, WebhookNotification, and WebhookAdvanced are statically imported and unconditionally mounted by Nav.jsx (gated only by internal Zustand `mode`/`open` state, never by `perms.webhooks`), WebhookMarker/WebhookAreaSelection are statically imported by the map's core Container.jsx, and useSyncData is imported unconditionally by GymPopup.jsx. A grep of the whole src tree shows exactly one React.lazy call in the entire app (the Playground page) — none in webhooks. All 3,796 lines, plus the MUI Autocomplete/Accordion/Dialog machinery they pull in, ship to every logged-in user's main bundle whether or not they have webhook permission; the server does compute a `webhooks: !!selectedWebhook` boolean at map load via `validateSelectedWebhook` (server/src/utils/validateSelectedWebhook.js, called from the `fabButtons` resolver at resolvers.js:175) that could gate a dynamic import, but nothing on the client currently reads it for that purpose. On the filter model: the webhook rule editor has its own storage entirely (`tempFilters`/`poracleValues`, Poracle's own field vocabulary like `pvp_ranking_league`), separate from the map's `filters: JSON` blob — but it is not fully independent. useGenFilters.js (hooks/useGenFilters.js:11-253) reads `useMemory.getState().filters` — the map's own filter store — to decide which pokemon/raid/quest/gym entries should even appear as trackable rows, reusing the map filter model's id-encoding convention (`pokemon_id-form`, `t{team}`, `r{level}`, `q{id}`/`c{id}`/`d{amount}`/`m{id}-{amount}`/`x{id}`) verbatim. That is a real cross-layer coupling worth flagging for the 2.0 filter-rules rework, since both sides of that convention are being redesigned independently. Separability verdict: the feature is otherwise well-isolated — one directory, its own store, its own query file, and only three files outside it reach in (Container.jsx, Nav.jsx, GymPopup.jsx). Turning it into a lazy-loaded island bound to `perms.webhooks` is mechanical: wrap those three import sites in React.lazy/Suspense gated on the boolean the server already computes, which is closer to a day of focused work than a redesign. The bigger 2.0-relevant fact is that the wire payload on both directions is already schemaless JSON matching Poracle's own row shape — porting off GraphQL needs no new schema design, just typing the existing JSON in TS and swapping six Apollo hooks for REST/WebSocket equivalents; the real cost center for 2.0 is re-deriving useGenFilters' dependency on whatever the new filter-rules model becomes, not the transport swap.

## Flow 4 — Search and scan-on-demand

**Path:** Search-select and Scan-on-demand request paths

### Narrative

Two independent user actions, both starting in a MUI dialog and ending either as a client-side map jump or an outbound HTTP call from the Node process. Search: typing in the search Autocomplete debounces 250ms, then fires an Apollo `useLazyQuery` whose GraphQL document is chosen per-category by `Query.search()` (src/services/queries/index.js:161). The server's `search`/`searchQuest`/`searchLure`/`searchInvasion` resolvers gate on `perms`, then call `DbManager.search()`, which runs a radius-expansion loop: it queries every configured scanner-DB connection for the category in parallel (`runScannerSources`, `Promise.allSettled`), dedupes by id keeping the freshest `updated`, and if the result count is still under half the configured search limit it widens the search bbox and tries again — bounded by a per-model max radius and a hard 2-second wall-clock cutoff, not just the result count. Six of the seven searchable models (Gym, Pokestop, Nest, Portal, Station, and the Gym-search variants) always run pure Knex SQL against the scanner database; only Pokemon.search has a second path — if a Golbat "mem" endpoint is configured it POSTs the same bbox+search-term filter to Golbat's `/api/pokemon/search` HTTP endpoint instead of touching SQL. A `gyms` search additionally reverse-geocodes each hit through `geocoder.js`/`photonGeocoder.js` when the user has a webhook with a Nominatim URL selected. Picking a result calls `map.flyTo` and stashes `{category, id}` in `useMemory`'s `manualParams`; that value is read independently by `Clustering.jsx` (to force that marker out of its cluster group) and by each marker's `useForcePopup` hook (to auto-open its popup once mounted, then clear the state on close). Scan-on-demand: a FAB button flips `useScanStore`'s `scanNextMode`/`scanZoneMode` to `'setLocation'`, which mounts a draggable marker plus a ring of coordinates computed client-side by turf.js `destination()` calls (`getScanZoneCoords`/`getScanNextCoords`) around the dragged point. Every coordinate change re-runs `CHECK_VALID_SCAN`, which the server answers via `getValidCoords()` — an R-tree area-restriction check, purely advisory at this stage. Clicking "scan" flips the mode to `'sendCoords'`, which fires the `SCANNER_STATUS` lazy query. The server's `scanner` resolver re-checks permission, re-checks the cooldown (server-session-tracked, not the client's copy), re-validates every coordinate through `getValidCoords()` again (discarding client-invalid ones rather than trusting the earlier check), and only then calls `scannerApi()`, which is almost entirely `backendConfig.platform` branching (rdm / dragonite / custom) building a different URL, body shape, and auth header for each, then performing the actual outbound `fetch()` to the scanner backend.

## Flow 5 — Login to authenticated request

**Path:** Login (Discord/Telegram/Local) → passport session → per-request perms → area-restricted query, in ReactMap 1.50.1

### Narrative

On boot, server/src/index.js:50 calls state.setAuthClients() (server/src/services/state.js:22-57), which for every enabled entry in config `authentication.strategies` requires server/src/strategies/{discord,telegram,local}.js, instantiates a DiscordClient/TelegramClient/LocalClient (each extends AuthClient, server/src/services/AuthClient.js), and calls initPassport() on it, which does `passport.use(name, new Strategy(...))`. This registers a global passport strategy per named auth method — nothing web-request-shaped yet. Separately, server/src/routes/authRouter.js:12-127 (loadAuthStrategies, called once at module load, line 129) walks the same config list and, for each enabled strategy, wires two Express routes: GET/POST `/auth/:name` (kicks off `passport.authenticate`) and `/auth/:name/callback` (the OAuth/local callback). Discord and Telegram get GET routes (browser redirect flow); local gets POST (form submit). Both sessionMiddleware() (server/src/middleware/session.js) and initPassport(app) (server/src/middleware/passport.js:11-14, `passport.initialize()` + `passport.session()`) are mounted on the whole `app` in index.js before `rootRouter`, so every request — REST or the separately-mounted `/graphql` — gets session hydration and passport deserialization for free.

A Discord login starts with the client rendering `<DiscordButton href="/auth/discord/callback">` (its href is actually the _first_ URL, `data.config.customRoutes.discordAuthUrl`, populated server-side; src/pages/login/Methods.jsx:29, src/components/auth/Discord.jsx). Clicking it is a plain anchor navigation to `/auth/discord`, which authRouter.js:42-48 hands to `passport.authenticate('discord', {successRedirect:'/', failureRedirect:'/', prompt:...})`, redirecting the browser to Discord's OAuth consent screen. Discord redirects back to `/auth/discord/callback?code=...`. authRouter.js:49-110 runs a small pre-check for the "silent auth needs interaction" retry loop (discord `clientPrompt:'none'` case, using `req.session.discordPromptRetry`), then calls `passport.authenticate('discord', ..., (err, user, info) => {...})`, which drives passport-discord's OAuth token exchange and invokes DiscordClient.authHandler (server/src/services/DiscordClient.js:271-400) as the verify callback with the Discord `profile`.

authHandler builds a `discordUser` object and calls `this.getPerms(profile)` (DiscordClient.js:130-240): if the Discord id matches `strategy.allowedUsers` (or a hardcoded base64-obfuscated id), every perm in config `authentication.perms` is force-granted (`admin: true`); otherwise it checks `blockedGuilds` membership (sets `perms.blocked`), then for each `allowedGuilds` guild the user belongs to, fetches their Discord role ids via `getUserRoles` (a live Discord.js guild-member fetch) and cross-references each configured perm's `roles` list (or `alwaysEnabledPerms`, or an active trial's `trialPeriod.roles`) to flip perm booleans. In the same pass it also calls areaPerms(userRoles) (server/src/utils/areaPerms.js) to build `perms.areaRestrictions`, webhookPerms/scannerPerms/scannerCooldownBypass (server/src/utils/{webhookPerms,scannerPerms}.js) for `perms.webhooks`/`perms.scanner`/`perms.scannerCooldownBypass`. This is the perms COMPUTATION point for Discord logins — it runs fresh on every login/callback, not once at account creation. If `perms.map` is false or `perms.blocked` is set, authHandler calls `done(null, undefined, info)`, and authRouter.js:80-85 redirects to `/blocked/...` instead of logging in. Otherwise it queries `state.db.models.User` (Objection/Knex, server/src/models/User.js) by `discordId` (or by `req.user.id` if this is an account-link, see below), inserts a new row if none exists (`strategy:'discord'`), and calls `done(null, {...discordUser, ...userExists, id: userExists.id})`.

Back in authRouter.js:88, passport's `req.login(user, cb)` runs `passport.serializeUser` (server/src/middleware/passport.js:16-18), which literally stores the whole user object — including the just-computed `perms` — as `done(null, user)`; express-session then persists the entire `req.session` (containing `session.passport.user`) into the session store. That store is either a MySQLStore against `database.settings.sessionTableName` (server/src/middleware/session.js:15-31, when a `user`-tagged DB schema is configured) or express-session's in-memory default otherwise; either way this is the perms STORAGE point — a JSON blob keyed by the `reactmap1` cookie's session id. server/src/models/Session.js's `json_extract(data, '$.passport.user...')` queries (isValidSession, clearDiscordSessions, clearOtherSessions, clearTrial, clearNonDonor) confirm that exact shape. The login callback also checks `state.db.models.Session.isValidSession(user.id)` and, if the user already has too many sessions (`api.maxSessions`), calls `clearOtherSessions` to invalidate the rest — then redirects to `/`. The browser now holds a `reactmap1` session cookie; that redirect is the "session cookie the client can use."

Every subsequent request — REST or GraphQL — goes through `passport.session()`'s deserializeUser (passport.js:20-26): it loads `req.session.passport.user` from the store (no recomputation) and, if `user.perms.map` is truthy, sets `req.user = {...user, username: getUserDisplayName(user)}`; otherwise deserialization fails (effectively logs the user out). This is the perms READ point for every authenticated request. Two call sites read `req.user.perms` (falling back to `req.session.perms` when unauthenticated): rootRouter.js:195 (`GET /api/settings`) and server/src/middleware/apollo.js:19 (the Apollo Server 5 request context). For anonymous or auth-disabled setups, rootRouter.js:128-171 (`/api/settings`) computes a default `req.session.perms` directly from `authentication.alwaysEnabledPerms` and unrestricted scanner modes — this is the perms COMPUTATION point for the no-login path, re-run on every `/api/settings` call (not cached beyond the session).

The client learns its own perms only through `GET /api/settings`. src/components/Config.jsx mounts once (React effect, line ~172), calls getSettings() (src/services/fetches.js:11-26), and on success calls `useMemory.setState({ auth: { perms: data.user.perms, methods: data.authentication.methods, loggedIn: !!data.user.loggedIn, ... } })` (Config.jsx:104-122), populating the Zustand `useMemory` store's `auth` slice (src/store/useMemory.js:87-104). That JSON also carries `data.menus`, `data.clientMenus`, `data.ui` — the server-generated UI descriptions from server/src/ui/{drawer,clientOptions,advMenus}.js, which are already perm-filtered server-side (getServerSettings.js:20,64,67 pass `user.perms` into `clientOptions`/`advMenus`/`drawer`). So the client doesn't just get boolean flags to check — it gets a pre-pruned menu/drawer tree; perms enforcement is partly "what got shipped," not just "what got hidden." The client never independently verifies or recomputes perms, and there's no live-refresh path: LinkAccounts.jsx (src/features/profile/LinkAccounts.jsx:78) forces a full `window.location.reload()` after any perms-affecting action, which re-triggers the same Config.jsx → `/api/settings` round trip.

Area restrictions travel from config to an actual SQL constraint as follows: config `authentication.areaRestrictions` is an array of `{roles, areas}` mappings. areaPerms(userRoles) (server/src/utils/areaPerms.js:8-31) turns a user's Discord roles / Telegram groups / local status into a flat list of allowed area names (an empty `areas` array on a matching restriction means "no access," short-circuiting to `[]`), stored as `perms.areaRestrictions` exactly as described above. On each data query, model files (server/src/models/{Pokemon,Gym,Pokestop,Station,Nest,...}.js) destructure `perms.areaRestrictions` from the GraphQL resolver's `perms` context and call getAreaSql(query, areaRestrictions, onlyAreas, category) (server/src/utils/getAreaSql.js:13-52): it consolidates the restriction list against `config.areas` (via consolidateAreas), and for each resolved area whose polygon exists in `config.areas.polygons`, adds `query.andWhere(...).orWhereRaw("ST_CONTAINS(ST_GeomFromGeoJSON(...), POINT(lon, lat))")` — a raw MySQL/MariaDB spatial predicate appended directly to the Objection/Knex query builder. If `authentication.strictAreaRestrictions` is on and the user has zero areas, getAreaSql returns false and the caller skips the query entirely (empty result). A parallel in-memory variant, filterRTree (server/src/utils/filterRTree.js) plus areaRestrictionsDenyAll, does the same allow/deny logic for R-tree-cached (non-SQL) data paths.

Account linking (Discord + Telegram + local on one User row) happens by revisiting a provider's OAuth flow while already logged in. In DiscordClient.authHandler (DiscordClient.js:328-367), if `req.user` exists and the User row found by discordId (`userExists`) has `strategy === 'local'`, it updates `req.user`'s row with `discordId`, `discordPerms` (JSON-stringified), `webhookStrategy:'discord'`; if a _separate_ pre-existing Discord-strategy user row shares that same discordId, its Badge rows are reassigned to `req.user.id` (server/src/models/Badge.js update `userId`), its `data` blob is copied over if `req.user`'s `data` is still null, and the duplicate row is deleted. The merged session perms become `mergePerms(req.user.perms, discordUser.perms)` (server/src/utils/mergePerms.js:8-29 — unions array-valued perms like `areaRestrictions`/`webhooks`/`scanner`, OR's booleans). TelegramClient.authHandler (TelegramClient.js:146-171) does the analogous update (telegramId/telegramPerms/webhookStrategy) but does not carry over Badge rows or the `data` blob — only the perms merge and duplicate-row deletion. LocalClient.authHandler (LocalClient.js:84-134), on a normal local login (no `req.user` involved), instead reads back any previously-linked `discordPerms`/`telegramPerms` JSON columns off the matched User row and folds them into the freshly computed local perms via the same mergePerms — so a user who logs in locally still inherits perms earned via a linked Discord/Telegram identity. All of this state lives in the User table's `discordId`/`telegramId`/`discordPerms`/`telegramPerms`/`strategy`/`webhookStrategy`/`selectedWebhook`/`data` columns plus the Badge table's `userId` FK; nothing here touches Session rows directly except that Discord's `guildMemberRemove`/`guildMemberUpdate` listeners (DiscordClient.js:41-85) call `Session.clearDiscordSessions` and `User.clearPerms` when a linked Discord user leaves the guild or loses a perm-relevant role, forcing re-authentication.

Independence from GraphQL: everything from the login button through a usable session cookie — authRouter.js, passport.js, session.js, all three strategy files (discord/telegram/local.js), DiscordClient/TelegramClient/LocalClient/AuthClient/Trial, mergePerms/areaPerms/webhookPerms/scannerPerms, and the User/Session/Badge models — is plain Express + passport + Objection/Knex, with zero GraphQL involvement; it would survive a transport change (e.g. to native WebSocket) untouched. `/api/settings` (rootRouter.js) is likewise already REST. The one place in this trace that is GraphQL-shaped is server/src/middleware/apollo.js's context function: it parses `req.body.query` with graphql-js's `parse()` to pull the operation name/type (for client-version gating and the mutation/`session_expired` checks) and throws `GraphQLError`s with Apollo-specific error codes. The `perms` value it forwards, though, is read via the exact same `req.user ? req.user.perms : req.session.perms` expression used in rootRouter.js — so the perms-sourcing line is transport-agnostic even though its error-signaling wrapper is not. Similarly, the area-restriction filtering inside resolvers.js:367-386 (trimming the `scanAreas` GeoJSON feature list down to `perms.areaRestrictions`) is GraphQL resolver code today, but the comparison logic itself is ordinary JS that could be lifted as-is into a WebSocket handler; getAreaSql/consolidateAreas/filterRTree are coupled to the Objection/Knex SQL-scanner-model layer (flagged for deletion under the Golbat-only 2.0 target) rather than to GraphQL, so their survival depends on whether Golbat's HTTP/gRPC responses still get geometry-filtered the same way or whether that filtering moves server-side into Golbat itself.

### Refactor notes

- **Perms are computed once per login/callback and then frozen into the session store's JSON blob; deserializeUser never recomputes them. The only invalidation paths are explicit (Discord guildMemberRemove/Update listeners, or the trial-manager's own timers) — a Telegram group removal or a local-status change has no equivalent live invalidation.**  
  _Evidence:_ server/src/middleware/passport.js:20-26 (pure blob read); server/src/services/DiscordClient.js:41-85 (Discord-only invalidation); no analogous listener exists in TelegramClient.js or LocalClient.js.  
  _Bears on:_ Any 2.0 rework of permissions into normalized, user-authored 'rules' tables must decide whether perms become live-computed per request (breaking the current frozen-session-blob model) or stay snapshot-at-login with an explicit invalidation hook per provider, not just Discord.
- **The perms-sourcing expression `req.user ? req.user.perms : req.session.perms` is duplicated verbatim in rootRouter.js:195 and apollo.js:19, with no shared helper.**  
  _Evidence:_ server/src/routes/rootRouter.js:195; server/src/middleware/apollo.js:19

  _Evidence:_ server/src/services/DiscordClient.js:341-354 (badges + data merge) vs server/src/services/TelegramClient.js:146-157 (no equivalent block)  
  _Bears on:_ Not a security finding, but a real behavioral asymmetry a rewrite could either accidentally fix (changing observed behavior) or accidentally miss (perpetuating an inconsistency) if the Telegram path isn't read as closely as Discord's during a rewrite.
- **LocalClient.authHandler silently auto-registers a brand-new account whenever a POSTed username doesn't already exist, using the submitted password as that new account's password — there is no separate 'register' step or confirmation.**  
  _Evidence:_ server/src/services/LocalClient.js:56-82

  _Evidence:_ grep across server/test/\*.test.js found no direct references to DiscordClient, LocalClient, TelegramClient, mergePerms, areaPerms, authRouter, or passport; none of these files appear in the provided HOT-churn list.  
  _Bears on:_ For the 2.0 rewrite, this is the highest-risk area to touch blind: any refactor of permission computation or session storage is working from spec-reading alone, with no regression suite and no recent-change history to lean on for 'what actually matters here.'
- **getAreaSql's spatial filtering (`ST_CONTAINS(ST_GeomFromGeoJSON(...))`) is built as a raw SQL string interpolated with `JSON.stringify(areas.polygons[area])` directly into the query, coupled to the Objection/Knex + MySQL/MariaDB scanner-schema layer slated for deletion under the Golbat-only 2.0 target.**  
  _Evidence:_ server/src/utils/getAreaSql.js:40-50  
  _Bears on:_ Area-restriction enforcement is currently inseparable from the SQL-scanner-model layer being deleted; the 2.0 design needs an explicit answer for where polygon-containment filtering happens once Golbat is the only data source (client-side, in a Golbat query parameter, or reimplemented server-side against Golbat's response) — right now nothing in this repo answers that.

## Completeness — surface no flow reached

By the dossier's own file-level accounting, the five traces name roughly 122 files summing to ~26,200 lines out of 68,087 total — about 38%. That number overstates real coverage: several of the largest 'covered' files (resolvers.js 868 lines, Poracle.js 1260, DbManager.js ~900, Pokemon.js ~1000, WebhookAdv.jsx 908, scannerApi.js 392) were only partially walked — a handful of functions/branches narrated out of each, not the whole file. Counting actual step-by-step line coverage rather than 'file was named,' true coverage is closer to 15-20% of the codebase. Roughly 60-65% of the repo — including some of the most 2.0-relevant code in it — was never opened by any trace.

The most consequential blind spot is not a forgotten corner but the opposite: the traces are Pokemon/GraphQL-centric enough that they missed a change already merged four weeks before this audit (2026-07-29) that partially delivers the 2.0 target itself — the Golbat HTTP DNF-filter path for gyms/pokestops/stations (server/src/filters/fort/_, server/src/filters/builder/_, plus Golbat branches inside Gym/Pokestop/Station/Pokemon.getAll), with SQL as the fallback rather than the primary path. A 2.0 plan built only from this dossier would treat 'Golbat-only, SQL deleted' as unstarted greenfield work rather than as 'finish what's half-shipped and delete the SQL fallback.' Two supporting blind spots compound this: packages/types (scanner.d.ts, server.d.ts — both HOT-churn files) already encodes much of the schema a rewrite would want, and packages/config's mutation/validation layer is the closest existing analog to the 'schema with defaults' target — neither was opened.

Secondary blind spots, roughly in order of rewrite risk: (1) every entity type besides Pokemon/Gym — station, route/wayfarer, tappable, nest, weather, device, s2cell, scanArea/scanCell, spawnpoint, portal — has its full popup/tile/marker client logic (well over 6,000 lines, including station's battle-state machine and tappable's per-category display rules) completely untraced; (2) three of the four GraphQL schema files (map.graphql, scanner.graphql, index.graphql — everything except poracle.graphql) were never read, which matters because 2.0 deletes GraphQL entirely and these are the inventory of what needs a WebSocket/delta equivalent; (3) live config-reload with genuine multi-domain/multi-tenant support (watcher.js, reloadConfig.js, multiDomainsObj) is invisible in every trace and would silently break under a naive schema-first config rewrite; (4) an operator-facing custom-file override mechanism (any `Foo.custom.jsx` silently replaces `Foo.jsx` at build time) is a real extensibility contract that a restructured TS tree would break with no compiler signal; (5) a secret-gated admin REST API (users/sessions/trial/config/area) is an external tooling contract outside the browser app that nobody examined. Lower-risk but still fully unexamined: tutorial/onboarding, backups, nest submissions, holiday effects, Sentry/analytics/desktop-notifications/error-boundary infra, the locale generation pipeline, and the playground/data/locales admin pages.
